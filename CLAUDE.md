# CLAUDE.md — Wedding Website

Mobile-first wedding website: a public site for guests (info, events, travel, FAQ, RSVP) and a private admin dashboard for the couple (guests, invitations, RSVPs, content).

The full product specification is in `docs/SPEC.md`. Read the relevant section before working on a feature. Section 14 (MVP) defines the first release; section 13 is the roadmap.

## Stack

All free tiers or open source:

- Next.js (App Router) + TypeScript + React, Tailwind CSS
- PostgreSQL on Neon (free tier), Drizzle ORM
- Better Auth for admin login (email allowlist, no public sign-up)
- Zod for validation
- Vitest (unit/integration) + Playwright (e2e)
- Hosting: Vercel Hobby plan
- Package manager: npm

Next.js 16 has breaking changes from older versions. See @AGENTS.md and read the relevant guide in `node_modules/next/dist/docs/` before writing Next.js code.

## Commands

- `npm run dev` — dev server
- `npm run lint` — ESLint
- `npm run typecheck` — generates route types, then `tsc --noEmit`
- `npm run build` — applies database migrations, then production build
- `npm run db:generate` — create a migration from `src/db/schema.ts` changes. Adding a required column to a table that has rows needs the generated SQL edited by hand: add it nullable, fill it in, then set `NOT NULL` (see `drizzle/0011_invitation_link_names.sql`)
- `npm run db:migrate` — apply migrations to the database in `.env.local` (development)
- `npm run db:studio` — browse the database
- `npm test` — Vitest unit tests (`src/**/*.test.ts`)
- `npm run test:e2e` — Playwright tests (`e2e/`, mobile viewport) against a dev server on port 3100 and the development database; with a dev server already running, `E2E_PORT=<its port> npm run test:e2e`. Tests that need data create fictional records and delete them afterwards (`e2e/invitation-page.spec.ts`, `e2e/rsvp-flow.spec.ts`; import `./load-env` before `@/db`, and run the file serially). First run: `npx playwright install chromium`
- `npm run invite:test -- "Household" "First Last" ["First Last" ...] [--plus-one]` — create a test household with one or more guests in the development database, and print its invitation link

## Layout

- `src/app/` — App Router routes
- `src/db/` — Drizzle schema and client (`auth-schema.ts` is generated by the Better Auth CLI); `drizzle/` — SQL migrations
- `src/app/admin/` — admin pages and server actions; `src/lib/auth.ts` — Better Auth config; `src/lib/admin/` — `requireAdmin()` (`session.ts`) and admin data loaders. Every admin page, server action, and data loader calls `requireAdmin()`. With Cache Components, put session-reading components inside `<Suspense>`.
- `src/app/admin/invitations/` — new, edit, delete, and correct-RSVP pages; `src/app/admin/export/` — CSV export route; `src/app/admin/password/` — change password; `src/app/admin/activity/` — audit log; `src/components/admin/` — admin forms, password fields, invitation links, and the invitation list
- Audit log: every admin change and export adds a record with `auditEntry()` (`src/lib/admin/audit.ts`), inside the same `db.batch` as the change. Summaries come from `src/lib/admin/audit-summary.ts`: invitation names and counts only, never dietary or accessibility notes, contact emails, or messages. A new admin action needs a new `AuditAction` and a label on the Activity page
- `src/app/invitation/[linkName]/` — public personal invitation page. Its greeting comes from `src/lib/invitation-greeting.ts` (one or two guests by full name, three or more by invitation name plus "Family"), and an unknown link gets one generic message. Its watercolor background (`src/assets/invitation-background.jpg`) is placed by `src/components/invitation-decor.tsx`, a decorative layer behind the card text `src/lib/invitation-link.ts` makes and checks link names (no database access, so scripts and unit tests can import it); `src/lib/invitation-lookup.ts` is the server-only lookup
- `src/lib/rsvp/` — guest RSVP lookup, validation, and saving
- `src/content/` — Our Story text and photos (`story.ts`, `engagement.ts`). A story photo can set `position` (a CSS object-position) when its subject is off center. The engagement gallery (`src/components/story/photo-gallery.tsx`) is an even grid laid out from each photo's width and height, and leaves out the proposal photo
- `e2e/` — Playwright tests
- `src/assets/` — photos. Banners are resized to about 2400px wide (`sips -Z 2400`); full-size originals stay out of git
- `.agents/skills/` — Neon agent skills (linked from `.claude/skills/`, pinned in `skills-lock.json`)
- Routes with dynamic params (such as `/admin/invitations/[id]/...`) are only known at request time: read `params` inside `<Suspense>`, and keep anything calling `usePathname()` (the site nav, and `GuestWeddingChat`, which hides the chat under `/admin` and on invitation pages) inside `<Suspense>`, or the build fails. Hide things per route by URL, not with CSS like `:has()`: Next keeps visited pages in the DOM, hidden, after you navigate away.
- Databases: Neon `wedding-db` for development, `neon-bole-zebra` for preview and production. Production secrets cannot be pulled locally; production migrations run in the Vercel build.
- Vercel variables marked sensitive (`ADMIN_EMAILS`, `ADMIN_SETUP_CODE`, `DATABASE_URL`, ...) cannot be read back, even in the dashboard. `vercel env update` replaces the whole value, so get the full current value (such as every admin email) from the user first. A change applies only after a redeploy (`vercel redeploy <deployment url> --target production`).
- Build and dev troubleshooting:
  - If `npm run build` fails with `next/font/google` errors although nothing font-related changed, the Turbopack cache was corrupt once (2026-10-21). Moving `.next/cache/turbopack` aside fixed it. A stale cache can also leave out a new `globals.css` theme color (such as `--color-gold`) while new classes still build; check the built CSS in `.next/static/chunks/`
  - If the dev server reports that a newly added export "is not a function" while a fresh build works, restart the dev server (deleting `.next/dev` if needed).
  - `next build` type-checks `e2e/` too, and a type error there stops the build after "Compiled successfully" (then `next start` finds no production build). Read the full build output, not just the compile line.
- `docs/SPEC.md` — product specification
- `PLAN.md` — current build plan; check off items as they are completed

## Non-negotiable rules

- Enforce authorization on the server for every protected operation. Never rely on client-side checks or hidden fields.
- Never expose the guest list, or another household's data, through public pages or APIs.
- Invitation tokens must be unpredictable, validated on the server, scoped to one invitation, and revocable.
- Use generic error messages for invalid invitation lookups.
- Never show an RSVP confirmation before the response is persisted.
- Keep "awaiting response" distinct from an explicit decline.
- Do not hardcode secrets, real guest data, or personal information. Use clearly fictional test data.
- Do not invent hotel rates, availability, or booking details.
- Never send real emails from test or development environments without explicit configuration.

## How to work

1. Inspect the existing codebase before proposing or implementing architectural changes.
2. If a critical product decision is unknown, ask a focused question rather than inventing business rules. For noncritical decisions, use sensible defaults and document them.
3. Present a short plan for substantial changes, then implement in small, testable increments.
4. Prefer simple, reusable components. Avoid unnecessary dependencies and infrastructure.
5. Add or update tests when changing important business logic (RSVP, eligibility, tokens, authorization).
6. Run tests, lint, type checking, and build after changes. Fix regressions before declaring work complete.
7. Update docs and `.env.example` when configuration changes.
8. Never claim deployment, email delivery, authentication, or database operations work unless verified. After a push, confirm a deployment exists for that commit (`vercel ls -m githubCommitSha=<full sha>`) and that the live site serves the change.
